## 3. 아키텍처 흐름 관련

| 항목 | 발표 주장 | 실제 코드 | 판정 |
|------|-----------|-----------|------|
| LangGraph fan-out | gate → 5전문가 병렬 | `agents/graph.py:37-42`: `for expert in _EXPERTS: graph.add_edge("gate", expert)` | ✅ |
| GateNet 코드 존재 | "코드에 있지만" | `agents/gate_agent.py` 실제 존재 | ✅ |
| GateNet 동작 방식 | "fan-out 방식을 택해 라우팅 오류 방지"(Q4) | **gate_node가 graph에 실제 포함·실행됨.** `screener → gate → experts` 흐름. gate는 Top-1 라우터가 아닌 전문가별 가중치를 계산하고 aggregator가 이를 활용 | ⚠️ |
| JSON 출력 필드 | `signal/confidence/target_return/risks/reason` | 실제 필드: `signal, confidence, target_return, horizon_days, score, reason, pros, cons`. **"risks"는 존재하지 않고 "cons"를 사용. "pros" 필드 미언급** | ⚠️ |

### ⚠️ GateNet 설명 상세 해설

Q4 답변에서 "저희 구현엔 비슷한 Gate 분류 프롬프트가 코드에 있지만, 발표 기준 시스템은 fan-out 방식"이라고 서술하여 **gate가 실제 미사용인 것처럼** 들릴 수 있다. 그러나 `graph.py`에서 `gate_node`는 `screener` 다음에 실제로 실행되며, 산출한 `gate_weights_map`은 `aggregator_node`의 `composite_score` 계산에 사용된다. 정확한 설명은: "gate는 Top-1 라우팅이 아닌 전문가별 가중치 산출 용도로 실행되며, 결과는 최종 집계에 반영된다."

## 9. 최우선 수정 사항 (발표 전 필수)

### 🔴 HIGH — 질문 받으면 치명적

1. **적중률 83% (S16, 암기카드)**: 실제 2025 통합 적중률은 **63%**, 성장주는 **55%**다. 83%는 어떤 데이터에서도 확인되지 않는다. 이 수치를 쓰면 청중이 summary_monthly.txt 같은 자료를 보면 즉시 반박 가능하다.  
   → **63% (통합) 또는 55% (성장주)로 수정**하거나, Sortino·ARR 등 다른 지표로 대체할 것.

2. **RAG DB "약 15만 건" (스크립트 S13, 암기카드)**: 스크립트와 암기카드에 "DB는 약 15만 건 규모입니다"라고 명시되어 있으나 실제 ChromaDB 건수를 검증한 흔적이 없다. 청중이 "몇 건인지 정확히 아세요?"라고 물으면 답변이 막힌다.  
   → 발표 전 아래 코드로 실제 건수를 확인하고 수치를 교체할 것:
   ```python
   from vector_store.store import PatternStore
   print(PatternStore().count())
   ```

### 🟡 MEDIUM — 혼란 가능성 또는 약점

3. **GateNet 설명 (Q4)**: "코드에 있지만" 식의 표현이 gate가 미사용인 것처럼 들린다. 실제로는 `screener → gate → 전문가 5개 병렬 → aggregator` 흐름으로 gate가 **실행되어 가중치를 계산**하고 최종 집계에 반영된다.  
   → "gate는 Top-1 라우팅 대신 전문가별 가중치 산출 용도로 실행되며, 최종 복합점수에 반영된다"로 수정.

4. **벤치마크 대비 알파 미산출 (Q10)**: "KOSPI200 대비 알파를 별도 산출하지 않았다"고 인정하는데, 이 질문이 Q&A에서 가장 날카롭게 들어올 수 있다. 2025년 KOSPI200 실제 연간 수익률을 조사해 "시장 수익률 대비 약 +N%p 초과"를 한 줄이라도 추가하면 방어선이 생긴다. 지금은 완전히 열려 있는 약점이다.  
   → KOSPI200 2025년 수익률(약 +20% 전후로 추정)을 찾아 슬라이드 또는 Q10 답변에 추가 권장.

5. **JSON 필드명 "risks"**: 실제 코드의 필드는 `cons`이며 `pros`도 함께 출력된다. `risks`라는 필드는 없다.  
   → "signal/confidence/target_return/reason/pros/cons" 또는 간략히 "신호·신뢰도·근거·리스크"로 표현 통일.

6. **포트폴리오 구성 흐름 설명 오류 (S15, 스크립트 S15)**: 발표에서 "confidence 0.6 이상 BUY만 모아 신뢰도 가중으로 **Top-20**을 만듭니다"라고 서술하나, 실제 흐름 및 config와 불일치한다.

   **실제 흐름 (`aggregator_node` 코드 기준):**

   ```
   ① 스크리너 → 전문가별 Top-15 후보
   ② 전문가 5명 × 최대 5종목 pick = 최대 25종목 (ticker 중복 가능)
   ③ 중복 ticker 통합 → signal=BUY AND confidence ≥ 0.60 필터
   ④ 복합점수 계산:
        composite = Σ(confidence × score × gate_weight) / n
                    + len(동의_전문가_수) × 0.5   ← 복수 전문가 동의 보너스
   ⑤ composite_score 내림차순 → Top-N 선택
        settings.yaml portfolio.top_n = 5  →  최종 통합 포트폴리오 5종목
   ```

   **복합점수 구성 요소:**
   - `confidence`: LLM이 출력한 BUY 신뢰도 (0.0~1.0)
   - `score`: LLM이 출력한 매력도 점수 (1~10)
   - `gate_weight`: GateNet이 해당 전문가에 부여한 적합도 (0.0~1.0)
   - 전문가 동의 보너스: 복수 전문가가 같은 종목을 BUY할수록 composite 상승 (전문가당 +0.5)

   **결론**: 발표에서 말하는 "Top-20"은 틀렸다. 통합 포트폴리오는 **최대 25종목 후보 → 조건 필터 → Top-5**가 정확한 표현이다. 단, 일일 대시보드(`report_20260519.txt`)가 20종목을 출력하는 이유는 daily_runner가 `build_portfolio()`의 기본값 `top_n=20`을 사용하기 때문으로 추정된다 — config와 일부 코드 경로 간 불일치가 존재한다.  
   → S15 설명을 "각 전문가 최대 5종목 × 5전문가 = 최대 25후보 → 복합점수 Top-5"로 수정할 것.
